# CASE-P001 — Project Fetch Prospective Stress Test v0.1

## Prospective Empirical Stress Test of IDOS Master Map v1.0

**Case ID:** CASE-P001  
**Case:** Anthropic Project Fetch — Can Claude train a robot dog?  
**Sampling Protocol:** CASE_SAMPLING_PROTOCOL_v0.1  
**Master Map Baseline:** MASTER_MAP_v1.0 — FROZEN  
**Selection Date:** 2026-10-02  
**Analysis Status:** First-pass stress test complete  
**Master Map Revision:** NONE

## 1. Purpose

CASE-P001 is the first prospective case selected under `CASE_SAMPLING_PROTOCOL_v0.1`.

The case was not selected because it appeared favorable, interesting, or especially compatible with IDOS.

It was selected by pseudorandom selection from a frozen eligible candidate pool using:

Random Seed: 20261002  
Selected Index: 2  
Candidate Pool Size: 8  
Selection Result: Anthropic Project Fetch

The purpose of CASE-P001 is not to demonstrate that IDOS can describe the case.

A sufficiently flexible conceptual framework can often be made to describe almost any case retrospectively.

The stronger question is:

> **Which parts of Master Map v1.0 remain necessary when the architecture is actively subjected to removal, redundancy, observability, and alternative-explanation tests?**

The analysis therefore deliberately attempted to remove IDOS concepts and architectural layers wherever the case could be described equally well without them.

## 2. Sampling Limitation

Random case selection does not imply unbiased sampling.

The eligible candidate pool was itself constructed through AI-assisted web search.

Therefore:

$$
\boxed{
\text{Random Selection}
\neq
\text{Unbiased Sampling}
}
$$

CASE-P001 should be treated as prospectively selected from the frozen candidate pool, while retaining the possibility of selection bias in candidate-pool construction.

This is recorded as a limitation of the current sampling protocol rather than hidden as methodological noise.

## 3. Evidence Boundary

The primary CASE-P001 reconstruction is limited to the original 2025 Anthropic Project Fetch experiment, in which two four-person teams attempted to program a quadruped robot to retrieve a beach ball, with one team having access to Claude and the other team not having access to Claude.

The 2026 Project Fetch Phase Two study is treated as later evidence and is excluded from the primary reconstruction.

Thus:

$$
\boxed{
\text{Primary Reconstruction}
=
\text{Original 2025 Project Fetch}
}
$$

and:

$$
\boxed{
\text{2026 Follow-up}
=
\text{Held Out from Primary Analysis}
}
$$

This rule is intended to reduce retrospective reinterpretation of the original case using later results.

## 4. Stage A — Theory-Neutral Reconstruction

Before applying IDOS terminology, the case was reconstructed without using:

- Difference
- Residual
- Holding
- Selection
- Update
- Reference Frame
- Boundary
- Possibility Space
- Trajectory
- Updating Unit
- CDP
- Relational Update
- System Update

The original experiment compared two four-person teams of Anthropic employees with limited robotics expertise.

One team had access to Claude.

The other did not.

The teams attempted increasingly difficult tasks involving a quadruped robot, including computer connectivity, sensor access, software development, robot control, localization, object detection, and attempted autonomous ball retrieval.

The Claude-assisted team generally progressed faster, completed more measured tasks, produced substantially more code, and progressed further toward autonomous retrieval.

The non-Claude team completed some individual subtasks faster and engaged in more human-to-human questioning.

Neither team completed the final autonomous retrieval objective.

The experiment also included physical-world failures and unexpected interactions between software behavior and the surrounding environment.

No IDOS conclusion was drawn during Stage A.

## 5. Stage B — Existing-Theory Baseline

Before applying Master Map v1.0, the case was examined using existing theoretical families.

Much of Project Fetch can already be described using:

- AI Augmentation
- Distributed Cognition
- Human-AI Teaming
- Team Cognition
- Exploration-Exploitation

For example:

- improved task speed does not require IDOS to explain;
- changes in team communication do not require IDOS;
- distributed Human-AI problem solving does not require IDOS;
- increased search and parallel exploration do not require Possibility-Space theory.

Therefore:

$$
\boxed{
\text{Project Fetch performance}
\not\Rightarrow
\text{IDOS validation}
}
$$

and:

$$
\boxed{
\text{Supported}
\neq
\text{Novel}
}
$$

This existing-theory baseline was retained throughout the subsequent analysis.

## 6. Falsification Matrix

Major Master Map concepts were classified using the following categories:

- **Supported** — observable facts are compatible with and give practical use to the distinction.
- **Redundant** — existing explanations are sufficient for the current case.
- **Unobservable** — the concept may apply, but available evidence cannot identify it.
- **Contradicted** — case evidence conflicts with the claim.
- **Not Tested** — the case does not expose the relevant phenomenon.

The most important result was that Master Map concepts did not receive uniform support.

Some concepts were empirically useful.

Some were unnecessary.

Some remained unobservable.

No architectural contradiction was identified.

## 7. Concept-Level Removal Test

The next test deliberately removed individual IDOS concepts.

For each concept C:

$$
IDOS-C
$$

was tested against CASE-P001.

The question was:

> **Can Project Fetch still be described with equivalent precision after removing this concept?**

### 7.1 Holding

Removing Holding caused little descriptive loss.

Search, uncertainty, delay, indecision, and task switching can describe the observed behavior without requiring a distinct Holding process.

**Result: REMOVE TEST — PASS**

### 7.2 Residual

Observed failures can currently be described as:

- error;
- mismatch;
- unresolved problem;
- failed attempt;
- Difference.

No observation in P001 required a distinct Residual construct.

**Result: REMOVE TEST — PASS**

### 7.3 Possibility Space

The Claude team explored more alternatives and generated more code.

However:

$$
\boxed{
\text{Exploration}
\neq
\text{Possibility Space}
}
$$

The observed phenomenon can currently be described through exploration-exploitation theory without invoking a distinct Possibility Space.

**Result: REMOVE TEST — PASS**

### 7.4 Translation Residual

Translation across:

$$
AI
\rightarrow
Human
\rightarrow
Code
\rightarrow
Robot
\rightarrow
Reality
$$

clearly occurs.

However, P001 does not yet identify a measurable quantity uniquely requiring Translation Residual.

**Result: REMOVE TEST — MOSTLY PASS**

### 7.5 Reference Frame

Different representations and feature selections appear relevant, but internal Reference Frames are not directly observed.

Much of the case can be described through ordinary perception, search, expertise, representation, or feature-selection language.

**Result: REMOVE TEST — PARTIAL PASS**

P001 does not establish the necessity of a distinct Reference Frame theory.

## 8. Concepts that resisted removal

### 8.1 Reality Recontact

Software or internal solutions did not guarantee successful physical-world behavior.

Examples included:

- a locally functioning object-detection approach failing under changed visual conditions;
- executable movement instructions producing unsafe physical behavior.

Thus:

$$
\boxed{
\text{Internal Success}
\neq
\text{Reality Validity}
}
$$

Removing Reality Recontact erased an important distinction.

**Result: REMOVE TEST — FAIL**

### 8.2 Relational Update

Claude access changed not only task performance but interaction structure.

Human-human questioning and Human-AI work patterns differed between experimental conditions.

Thus:

$$
Relation_{ij,t}
\rightarrow
Relation_{ij,t+1}
$$

contains empirically relevant information not captured by individual task-performance measures alone.

**Result: REMOVE TEST — FAIL**

### 8.3 Updating Unit Identification

The statement:

> the Claude team improved

does not identify what actually changed.

Possible units include:

- Human
- AI
- Team
- Human + AI
- Human + AI + Robot

Different choices produce different conclusions.

Therefore:

$$
\boxed{
\text{Team Performance}\uparrow
\not\Rightarrow
\text{Human Update}\uparrow
}
$$

**Result: REMOVE TEST — FAIL**

The case supports the need to identify the unit of analysis.

It does not yet establish that IDOS's specific Updating Unit theory is the only or best solution.

### 8.4 Observability / Verifiability / Updateability

The case contains meaningful distinctions among:

- Information Received
- Information Understood
- Information Verified
- Action Changed
- Reality Result

Collapsing all of these into information transfer loses relevant structure.

**Result: REMOVE TEST — FAIL**

The need for some distinction is supported.

The exact current DO / CFV / MU decomposition remains provisional.

### 8.5 System Update

This produced the strongest result.

The Claude-assisted team performed better on several task measures.

But simultaneously:

- interaction structure changed;
- code volume increased substantially;
- exploration increased;
- understanding remained uncertain;
- safety-relevant physical behavior occurred;
- final autonomous completion was not achieved.

Therefore:

$$
\boxed{
\text{Performance}\uparrow
\not\Rightarrow
\text{System Update}\uparrow
}
$$

Removing System Update reduces the case to a productivity comparison and loses the question:

> **What changed in the larger Human-AI-Team system?**

**Result: REMOVE TEST — STRONG FAIL**

However, System Update remains under-operationalized.

It currently generates a meaningful question more clearly than it generates a measurable answer.

### 8.6 Update ≠ Improvement ≠ Good

Task speed alone cannot determine whether all relevant properties improved.

Therefore:

$$
\boxed{
\text{Update}
\neq
\text{Adaptation}
\neq
\text{Improvement}
\neq
\text{Good}
}
$$

remained necessary to prevent performance improvement from being mistaken for overall value improvement.

**Result: REMOVE TEST — FAIL**

## 9. Concept-Level Result

### Concepts under demotion pressure

- Holding
- Residual
- Possibility Space
- Translation Residual, more weakly

These concepts were not required to describe CASE-P001 with comparable precision.

They should therefore remain under explicit removal pressure in future cases.

### Concepts with stronger retain pressure

- Reality Recontact
- Relational Update
- Updating Unit / Level
- Observation / Verification / Updateability distinction
- System Update
- Dynamics ≠ Evaluation

These distinctions materially changed the analytical structure of CASE-P001 when removed.

## 10. Architecture Removal Test

The test was then repeated at the frozen Master Map architecture level.

### 10.1 Ultimate Question

Removing the Ultimate Question still permits an ordinary AI-uplift analysis.

However, it eliminates the unifying question of heterogeneous system change.

**Result: PARTIAL FAIL**

**Retain pressure: Moderate**

### 10.2 Science of Reference Frames

Most of P001 can be described without explicit Reference Frame theory.

Internal Frames are not directly observed.

**Result: PASS / PARTIAL FAIL**

**Retain pressure: Weak**

This was one of the weakest upper-level results in P001.

### 10.3 General Theory of Update

A simpler:

$$

\rightarrow
Feedback
\rightarrow
Change
$$

Some change/update distinction remains useful, but CASE-P001 does not demonstrate the necessity of a distinct IDOS General Theory of Update.

**Result: PARTIAL FAIL**

**Retain pressure: Moderate**

### 10.4 Heterogeneous Interoperability

Project Fetch contains:

$$

\leftrightarrow
AI
\leftrightarrow
Software
\leftrightarrow
Robot
\leftrightarrow

$$

These systems do not require identical internal representations in order to interact.

Removing interoperability loses the common problem of tracing information and action across heterogeneous interfaces.

**Result: FAIL**

**Retain pressure: Strong**

### 10.5 Relational / System Update

Removing this layer reduces Project Fetch largely to:

$$
AI\ Access
\rightarrow
Task\ Performance
$$

and loses changes in team configuration and uncertainty over what system actually improved.

**Result: STRONG FAIL**

**Retain pressure: Very Strong**

### 10.6 Measurement

Without the Measurement layer, statements such as:

- the team updated;
- understanding changed;
- Possibility Space expanded;
- Human-AI capability improved;

risk becoming conceptual interpretation rather than empirically disciplined claims.

The case strongly reinforces the necessity of distinguishing:

$$
\boxed{
\text{Observed}
\neq
\text{Inferred}
\neq
\text{Unobservable}
}
$$

**Result: STRONG FAIL**

**Retain pressure: Very Strong**

### 10.7 Evaluation

Without evaluation distinctions:

$$

\Rightarrow
Better
$$

becomes an implicit assumption.

P001 does not support that simplification.

**Result: FAIL**

**Retain pressure: Strong**

### 10.8 Governance

CASE-P001 does not directly test legitimacy, sovereignty, institutional authority, contestability, or preservation decisions.

**Result: NOT TESTED**

### 10.9 Social Implementation

The case is an applied experiment but does not test the broader IDOS social-implementation architecture.

**Result: NOT TESTED / METHOD CANDIDATE**

### 10.10 Reality Recontact

The physical-world component of the experiment makes Reality Recontact particularly visible.

Removing it collapses the distinction between computational success and real-world validity.

**Result: STRONG FAIL**

**Retain pressure: Very Strong**

## 16. Research Implication

Before CASE-P001, one major IDOS hypothesis was that novelty, if present, might lie less in individual concepts than in the architecture connecting them.

CASE-P001 provides limited prospective evidence consistent with that hypothesis.

The case did not require several lower-level IDOS concepts.

Yet removing the higher-level distinctions among:

- heterogeneous systems;
- interfaces;
- Units;
- Relations;
- System;
- measurement;
- evaluation;
- Reality;

substantially reduced analytical precision.

The strongest current candidate contribution is therefore not:

> a universal sequence of cognitive processes.

It may instead be:

> **a cross-level architecture for tracing change across heterogeneous intelligences while preserving distinctions among Unit, Relation, System, Measurement, Evaluation, and Reality.**

This remains a research hypothesis.

## 17. Anti-Overfitting Rule

No Master Map concept should be revised solely to improve fit with CASE-P001.

Specifically:

$$
\boxed{
\text{P001 Residual}
\rightarrow
\text{Record}
\neq
\text{Immediate Repair}
}
$$

The current weaknesses should be carried forward unchanged into the next prospective case.

The next case should therefore test whether the same pattern recurs.

If concepts such as:

- Holding;
- Residual;
- Possibility Space;

continue to fail Removal Tests across multiple independent prospective cases, demotion or removal should be considered.

Likewise, if:

- Heterogeneous Interoperability;
- Relational / System Update;
- Measurement;
- Reality Recontact;

continue to resist removal across heterogeneous cases, the empirical basis for the upper architecture will become stronger.
