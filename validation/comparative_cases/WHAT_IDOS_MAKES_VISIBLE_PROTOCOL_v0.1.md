# WHAT_IDOS_MAKES_VISIBLE_PROTOCOL_v0.1

## Status

Experimental Validation Protocol v0.1

## Purpose

This protocol evaluates what becomes additionally visible when a case is analyzed through IDOS.

The objective is not to prove that IDOS is correct, superior, or universally necessary.

The primary question is:

\[
\boxed{
What\ does\ IDOS\ make\ visible?
}
\]

The secondary question is:

\[
\boxed{
When\ does\ IDOS\ become\ valuable?
}
\]

The protocol therefore focuses on differential visibility rather than theoretical confirmation.

---

# 1. Core Principle

For each case:

\[
Conventional\ View = X
\]

\[
IDOS\ View = X + Y
\]

where:

\[
\boxed{
Y = Incremental\ Visibility
}
\]

The purpose of the analysis is to determine whether \(Y\):

1. actually exists,
2. is materially different from conventional analysis,
3. requires IDOS concepts,
4. recurs across multiple cases,
5. becomes more pronounced under particular system conditions.

If no meaningful \(Y\) is found, that is a valid result.

---

# 2. Non-Confirmation Rule

The protocol must not be used to protect IDOS from falsification.

The following outcomes are all acceptable:

### Outcome A

Conventional analysis already captures nearly everything.

\[
IDOS \approx Conventional\ Analysis
\]

### Outcome B

IDOS provides additional terminology but little additional analytical value.

\[
IDOS = Re-description
\]

### Outcome C

IDOS reveals a recurring structural feature that is difficult to express through conventional analysis.

\[
IDOS = Incremental\ Visibility
\]

### Outcome D

IDOS becomes useful only under particular system regimes.

\[
Value_{IDOS}=f(System\ Regime)
\]

The preferred result is not predetermined.

---

# 3. Unit of Comparison

The comparison is not:

\[
IDOS\ vs\ One\ Existing\ Theory
\]

Instead:

\[
IDOS
\]

is compared against a reasonable combination of conventional analytical approaches appropriate to the case.

Examples may include:

- systems thinking
- sociotechnical systems analysis
- organizational theory
- governance analysis
- resilience engineering
- Human–AI teaming
- provenance analysis
- self-adaptive systems
- safety engineering
- institutional analysis
- network analysis
- control theory
- decision science

The conventional analysis should be as strong as reasonably possible.

IDOS must not be made to look useful by artificially weakening the comparison baseline.

---

# 4. Analytical Separation

Each case must be analyzed in the following sequence.

The stages must not be collapsed.

\[
\boxed{
Raw
\rightarrow
Conventional
\rightarrow
IDOS
\rightarrow
Difference
\rightarrow
Necessity
}
\]

This separation is intended to reduce hindsight contamination and IDOS-driven reconstruction.

---

# 5. Stage 1 — Raw Reconstruction

## Objective

Reconstruct what occurred using the available evidence before introducing IDOS terminology.

## Questions

Record:

- What happened?
- Which actors were involved?
- What decisions were made?
- What technologies or institutional structures were involved?
- What changed over time?
- What outcomes were observed?
- What failures, tensions, conflicts, or anomalies occurred?
- What evidence is direct?
- What evidence is interpreted?
- What remains unknown?

## Constraint

Avoid IDOS-specific terms whenever possible.

Do not initially describe events using terms such as:

- Updating Unit
- Dynamic Boundary
- Trajectory
- Future Updateability
- CFV
- MU
- Residual
- 12PDM

The purpose is to preserve an IDOS-independent reconstruction.

---

# 6. Stage 2 — Conventional Analysis

## Objective

Analyze the case using established concepts without relying on IDOS.

## Questions

Ask what a strong conventional analysis can already explain.

Examples:

- incentive failure
- coordination failure
- information asymmetry
- governance failure
- automation bias
- distribution shift
- organizational lock-in
- human oversight failure
- accountability gaps
- feedback-loop failure
- resilience loss
- institutional inertia
- power asymmetry
- temporal mismatch
- system complexity
- adaptation failure

## Required Output

Produce:

### 6.1 Conventional explanation

What does the conventional view explain well?

### 6.2 Conventional blind spots

What remains difficult to describe, connect, or observe?

Do not assume that such blind spots exist.

---

# 7. Stage 3 — IDOS Analysis

Analyze the same case using only the current IDOS v1.1 architecture.

No new concepts should be introduced during case analysis unless absolutely necessary.

The current analytical structure is:

## 7.1 Dynamics

### Updating Unit

What entity or relation is actually undergoing update?

Possible units may include:

- individual human
- AI system
- team
- organization
- Human–AI relation
- multi-agent network
- institution
- temporary coalition

Ask:

\[
What\ is\ actually\ updating?
\]

and:

\[
Does\ the\ Updating\ Unit\ change\ over\ time?
\]

---

## 7.2 Dynamic Boundary

Where is the operational boundary of the relevant system?

Ask:

- What lies inside the system at time \(t_1\)?
- What lies outside it?
- Does this distinction remain stable?
- Are decisions, memory, authority, or execution migrating across the boundary?

Represent conceptually as:

\[
B_t \neq B_{t+1}
\]

when appropriate.

---

## 7.3 Trajectory

Analyze the system longitudinally rather than only as a snapshot.

Ask:

- What sequence of updates produced the current state?
- Which past updates constrain the current state?
- Does present performance hide degradation elsewhere?
- Is the system entering an increasingly difficult-to-reverse trajectory?

\[
S_0
\rightarrow
S_1
\rightarrow
S_2
\rightarrow
\dots
\rightarrow
S_t
\]

---

# 8. Transition Driver — Difference

Identify differences capable of producing update.

Ask:

- What discrepancy became actionable?
- Who or what detected it?
- Was it ignored, compressed, translated, suppressed, or amplified?
- Did the difference propagate across agents or boundaries?

Difference should not automatically be treated as error.

It may be:

- disagreement
- anomaly
- prediction mismatch
- conflicting objective
- environmental change
- new information
- unmodeled outcome
- incompatible representation

---

# 9. Observability

## 9.1 Reference Frame

Ask:

\[
Observed\ from\ whose\ frame?
\]

Identify the frame from which performance, error, success, or risk is being judged.

Check whether different agents operate under different frames.

---

## 9.2 Measurement

Ask:

- What is being measured?
- What is not being measured?
- Is measurement driving system behavior?
- Has the measurement regime itself changed?
- Does increased AI involvement change what counts as observable?

---

## 9.3 Provenance

Ask whether the system retains the history required to reconstruct:

- how a decision was made,
- which information influenced it,
- which agent altered it,
- how representations changed,
- where responsibility or authority migrated.

Loss of provenance may reduce later revisability.

---

# 10. Second-Order Updateability

## Future Updateability

Definition candidate:

\[
\boxed{
Future\ Updateability
=
Capacity\ to\ revise\ the\ conditions\ of\ future\ revision
}
\]

This does not merely ask whether the system can update now.

It asks whether the system preserves its capacity to later change:

- decision rules,
- objectives,
- authority structures,
- measurement systems,
- model dependencies,
- boundaries,
- human roles,
- AI roles,
- escalation paths.

A system may show:

\[
Performance_t \uparrow
\]

while simultaneously showing:

\[
Future\ Updateability_t \downarrow
\]

This possibility should be explicitly tested.

---

# 11. Relational Capacities

## 11.1 CFV

CFV concerns whether claims, states, or outputs across agents can be meaningfully checked or compared.

Conceptually:

\[
CFV_{ij}
=
Capacity\ for\ Cross\text{-}Frame\ Verification
\]

The exact formal definition remains open.

The case analysis should ask:

- Can agent \(i\) inspect or verify agent \(j\)?
- Is verification technically possible?
- Is the evidence interpretable?
- Is provenance sufficient?

---

## 11.2 MU

MU concerns whether one agent can actually produce revision in another.

Conceptually:

\[
MU_{ij}
=
Mutual\ Updateability
\]

Ask:

- Can human feedback materially update the AI?
- Can AI outputs materially update human judgment?
- Can operational evidence update management policy?
- Can lower-level agents revise higher-level rules?
- Is the influence one-directional?

The distinction must be maintained:

\[
\boxed{
Verification \neq Influence \neq Update
}
\]

A system may allow verification without permitting meaningful update.

---

# 12. Cross-Cutting Conditions

## 12.1 Power

Ask:

- Who can define the frame?
- Who controls measurement?
- Who can change system rules?
- Who can override whom?
- Who bears consequences without possessing update authority?

Power must not be treated merely as another actor attribute.

It may shape the architecture of possible updates.

---

## 12.2 Temporal Compatibility

Ask whether relevant agents operate at compatible update speeds.

Examples:

\[
\tau_{AI} \ll \tau_{Human}
\]

or:

\[
\tau_{Market} \ll \tau_{Institution}
\]

Check for:

- review lag
- governance lag
- escalation lag
- regulatory lag
- human cognitive lag
- model retraining lag
- organizational adaptation lag

A system may technically retain feedback while becoming temporally incapable of using it.

---

# 13. External Grounding — Reality Contact

Ask whether the system remains coupled to external reality rather than only to its own internal representations.

Examine:

- external feedback,
- physical outcomes,
- customer behavior,
- social consequences,
- adversarial response,
- environmental constraints,
- unexpected outcomes.

A system may become internally coherent while losing reality contact.

---

# 14. Derived Properties

The following should normally be treated as derived rather than primary primitives.

## 14.1 Re-measurability

Can the system revise how it measures itself?

## 14.2 System Update

Does update occur at the level of the wider system rather than only within individual agents?

## 14.3 Continuity

Does the system preserve enough relational, historical, and operational continuity to remain revisable through change?

These should be inferred only when supported by the underlying analysis.

---

# 15. Diagnostic and Extended Concepts

## Residual

Residual is treated as a diagnostic primitive.

It may indicate:

- model mismatch,
- unresolved difference,
- translation loss,
- unexplained outcome,
- disagreement,
- prediction error.

Residual should not automatically be elevated to a universal causal mechanism.

---

## Holding

Holding is treated as a domain-dependent mechanism.

Use only where a case actually contains a meaningful process of preserving unresolved difference without premature closure.

Do not force Holding into every case.

---

## Possibility Space

Possibility Space is a generative extension.

Use only when the case requires explicit analysis of how the range of available future actions changes.

---

## 12PDM

The 12-process model is treated as a high-resolution observation and description protocol.

It should not be used automatically.

First test whether the lower-resolution v1.1 architecture is sufficient.

---

# 16. Stage 4 — Incremental Visibility Test

After both analyses are complete, compare them directly.

Construct:

\[
Conventional\ View = X
\]

\[
IDOS\ View = X + Y
\]

Then identify \(Y\).

For every proposed \(Y\), answer:

1. What exactly became visible?
2. Was it absent from the conventional analysis?
3. Was it merely expressed in different language?
4. Did IDOS connect facts that were previously separated?
5. Did it expose a temporal relation?
6. Did it expose a boundary transition?
7. Did it identify a changing Updating Unit?
8. Did it reveal loss of Future Updateability?
9. Did it distinguish verification from actual update?
10. Did it reveal measurement change?
11. Did it reveal propagation or blockage of update across agents?

---

# 17. Incremental Visibility Classification

Each claimed incremental insight should receive one of four provisional classifications.

## IV-0 — No Added Visibility

Conventional analysis already captures the insight adequately.

## IV-1 — Terminological Reframing

IDOS provides a clearer vocabulary but no major new analytical structure.

## IV-2 — Structural Integration

IDOS links previously separate observations into one coherent dynamic structure.

## IV-3 — Differential Discovery

IDOS reveals a materially important feature that was not readily visible through the conventional analysis.

The purpose of this classification is not to score IDOS globally.

It is to classify individual analytical outputs.

---

# 18. Stage 5 — Necessity Test

For every useful IDOS insight, remove concepts one at a time.

Test whether the insight survives.

Example:

\[
Insight_Y
\]

then remove:

\[
Updating\ Unit
\]

If the same insight remains fully expressible, Updating Unit was not necessary for that insight.

Repeat for:

- Updating Unit
- Dynamic Boundary
- Trajectory
- Difference
- Reference Frame
- Measurement
- Provenance
- Future Updateability
- CFV
- MU
- Power
- Temporal Compatibility
- Reality Contact
- Residual
- Holding
- Possibility Space
- 12PDM

Classify each concept as:

### N0 — Unnecessary

The insight survives unchanged.

### N1 — Helpful

The concept improves clarity but is not essential.

### N2 — Structurally Necessary

The insight materially weakens or disappears without it.

This test should be performed case by case.

---

# 19. Anti-Overfitting Rule

No new IDOS primitive should be added solely because one case is difficult to explain.

A new concept requires at least one of the following:

1. recurrence across multiple cases,
2. a clear logical necessity within the architecture,
3. inability of existing concepts to represent the phenomenon,
4. independent external justification.

Otherwise the observation should remain as:

\[
Open\ Residual
\]

rather than triggering immediate theory expansion.

---

# 20. Case Regime Classification

Each case should be assigned a provisional regime.

## R1 — Present Normal

Stable boundaries, recognizable roles, conventional organizational structure.

## R2 — Present Edge

High AI dependence or unusually adaptive digital systems, but still operating within mostly recognizable institutional boundaries.

## R3 — Transition

Roles, authority, decision rights, measurement, or Human–AI boundaries are actively changing.

## R4 — Agentic / Multi-Agent

Multiple autonomous or semi-autonomous agents interact and propagate decisions or actions.

## R5 — Future Regime Proxy

A present-day or simulated case containing structural properties expected to become more common under advanced AI or ASI conditions.

This classification is descriptive rather than evaluative.

---

# 21. Regime Sensitivity Test

After multiple cases, test:

\[
Value_{IDOS}(R1)
\]

versus:

\[
Value_{IDOS}(R2,R3,R4,R5)
\]

Possible hypothesis:

\[
Value_{IDOS}
\uparrow
\quad
as
\quad
Boundary\ Instability,
Updating\ Unit\ Change,
Temporal\ Mismatch,
and
Measurement\ Change
\uparrow
\]

This remains a hypothesis until supported by cases.

# 23. Five-Case Pilot

The first pilot consists of five deliberately differentiated regime cases.

The five cases are not intended to represent five arbitrary examples.

Instead, they are structured as a progression from relatively stable present-day Human–AI systems toward increasingly complex, dynamic, and future-oriented socio-technical regimes.

The regime sequence is:

\[
Present\ Normal
\rightarrow
Present\ Edge
\rightarrow
Transition
\rightarrow
Agentic/Multi\text{-}Agent
\rightarrow
Future\ Regime\ Proxy
\]

The purpose of this sequence is to test not only:

\[
Does\ IDOS\ add\ value?
\]

but also:

\[
When\ does\ IDOS\ become\ valuable?
\]

The five cases are therefore designed to examine whether the incremental visibility provided by IDOS changes as system boundaries, Updating Units, measurement regimes, temporal relationships, and forms of agency become more dynamic.

---

## Case 1 — Present Normal

A relatively conventional present-day AI implementation.

Typical characteristics:

- AI primarily functions as a support tool;
- human decision authority remains recognizable;
- system boundaries are comparatively stable;
- organizational roles remain clear;
- measurement is conventional;
- autonomous AI-to-AI interaction is limited or absent.

Purpose:

Establish a low-complexity baseline and test whether IDOS adds little or no incremental visibility under stable conditions.

---

## Case 2 — Present Edge

A contemporary system with materially deeper AI dependence.

Typical characteristics may include:

- substantial AI-mediated workflow;
- partial delegation of judgment;
- growing organizational dependence on machine-generated representations;
- reduced direct human inspection;
- emerging automation dependency;
- increased difficulty separating human and AI contributions.

Purpose:

Test whether IDOS begins to add visibility when AI moves from a support tool toward infrastructure.

---

## Case 3 — Transition

A system in which Human / AI / Organization roles, authority, responsibility, measurement, or operational boundaries are actively changing.

Typical characteristics may include:

- humans shifting from decision-makers to supervisors;
- AI shifting from recommender to executor;
- responsibility migrating across organizational boundaries;
- changing escalation structures;
- changing Updating Units;
- changing system boundaries.

Purpose:

Test Dynamic Boundary, Updating Unit, Trajectory, and Future Updateability under active structural transition.

---

## Case 4 — Agentic / Multi-Agent

A system involving multiple autonomous or semi-autonomous agents interacting across a distributed decision or execution structure.

The agents may include:

- AI agents;
- humans;
- organizations;
- automated services;
- machine-mediated institutions.

Typical characteristics may include:

- chained delegation;
- machine-to-machine interaction;
- distributed execution;
- limited end-to-end human visibility;
- fragmented provenance;
- asymmetric verification and update capacity;
- temporal mismatch across agents.

Purpose:

Test CFV, MU, Provenance, Temporal Compatibility, distributed update propagation, and blockage across agents.

---

## Case 5 — Future Regime Proxy

A present-day, simulated, experimental, or composite case that provides the strongest empirically defensible proxy for a future society in which AI, humans, organizations, and institutions are deeply interdependent and dynamically co-updating.

This case must not rely on unconstrained speculation.

It should instead combine structural properties that are already observable, reproducible, or traceable in present systems.

Relevant properties may include:

- autonomous agent interaction;
- dynamic delegation;
- rapidly changing operational boundaries;
- machine-generated measurement systems;
- high-speed AI decision cycles;
- reduced direct human observability;
- recursive workflow adaptation;
- AI-mediated organizational restructuring;
- provenance fragmentation;
- distributed governance;
- human oversight lag;
- machine-to-machine coordination;
- unstable Updating Units.

Purpose:

Test the strongest version of the current working hypothesis:

\[
IDOS\ becomes\ increasingly\ useful
\ when\
the\ unit,\ boundary,\ measurement,\ and\ conditions\ of\ update
\ themselves\ become\ dynamic
\]

The central question is:

\[
Does\ IDOS\ provide\ substantial\ incremental\ visibility
\ under\ conditions\ approximating
\ a\ deeply\ AI\text{-}entangled\ society?
\]

# 23A. Sampling Strengthening for the Five-Case Pilot

The five-case pilot is intentionally structured as a progression from present-day relatively stable Human–AI systems toward increasingly complex, dynamic, and future-oriented socio-technical regimes.

The five cases are therefore not treated as an undifferentiated sample.

Instead, each case belongs to a pre-defined regime stratum:

\[
Present\ Normal
\rightarrow
Present\ Edge
\rightarrow
Transition
\rightarrow
Agentic/Multi\text{-}Agent
\rightarrow
Future\ Regime\ Proxy
\]

The regime structure is theoretically defined in advance.

However, the individual case within each regime should not be selected solely because it appears favorable, interesting, or particularly compatible with IDOS.

To reduce case-selection bias, each regime should use the following sampling procedure:

1. define explicit inclusion criteria for the regime;
2. construct a candidate pool before selecting the final case;
3. freeze the candidate pool;
4. use a pre-specified mechanical selection procedure where practical;
5. record the candidate pool and selection procedure;
6. do not replace the selected case merely because it produces weak IDOS results.

This creates the separation:

\[
Theory\ defines\ the\ regime
\]

\[
Sampling\ selects\ the\ case
\]

The purpose is not statistical representativeness.

The purpose is to reduce confirmation-driven case selection while preserving theoretically meaningful regime variation.

---

# 23A.1 Case V001 — Present Normal Sampling

## Regime Purpose

V001 represents a relatively stable contemporary Human–AI system.

The expected characteristics are:

- AI primarily acts as a support tool;
- human operational authority remains recognizable;
- organizational boundaries remain comparatively stable;
- measurement systems are conventional and externally understandable;
- Human / AI roles are not undergoing major structural transition;
- autonomous AI-to-AI coordination is limited or absent.

Conceptually:

\[
Boundary\ Dynamism \approx Low
\]

\[
Updating\ Unit\ Instability \approx Low
\]

\[
AI\ Autonomy \approx Low
\]

\[
Measurement\ Change \approx Low
\]

## Inclusion Criteria

A candidate case should:

1. involve real-world AI deployment;
2. contain publicly accessible evidence sufficient for reconstruction;
3. have measurable operational outcomes;
4. preserve clear human decision or execution authority;
5. not depend primarily on autonomous multi-agent interaction;
6. represent a relatively conventional organizational deployment.

## Sampling Rule

A frozen candidate pool should first be created from multiple eligible contemporary AI implementation cases.

The final V001 case should then be selected using a pre-specified mechanical procedure where feasible.

V001 should not be selected because it demonstrates a known IDOS strength.

Indeed, a case in which conventional analysis performs well is desirable.

## Sampling Objective

V001 functions as a low-complexity baseline.

The key question is:

\[
Does\ IDOS\ add\ meaningful\ visibility
\ under\ relatively\ stable\ conditions?
\]

A weak or zero incremental result is fully acceptable.

---

# 23A.2 Case V002 — Present Edge Sampling

## Regime Purpose

V002 represents a contemporary system in which AI dependence has become materially deeper than in ordinary decision-support deployment.

The system should still be recognizably present-day, but AI should already influence important operational, informational, or organizational processes.

Expected characteristics include some combination of:

- substantial AI dependence;
- AI-mediated workflow coordination;
- reduced human direct inspection;
- partial delegation of judgment;
- growing dependence on machine-generated representations;
- emerging lock-in or dependency effects;
- increasing difficulty separating human and AI contributions.

Conceptually:

\[
Boundary\ Dynamism > V001
\]

\[
AI\ Dependence > V001
\]

\[
Human\ Direct\ Observability < V001
\]

## Inclusion Criteria

A candidate case should:

1. be based on an actually deployed system;
2. involve significant organizational dependence on AI;
3. show at least one emerging structural issue beyond simple productivity improvement;
4. retain enough public evidence for chronological reconstruction;
5. not yet require a fully hypothetical future scenario.

Relevant structural signals may include:

- automation dependency;
- algorithmic management;
- large-scale recommendation systems;
- AI-mediated decision processes;
- AI-generated operational prioritization;
- degraded human fallback capability;
- centralized model dependence.

## Sampling Rule

A candidate pool should be constructed from several qualifying high-dependence AI systems.

The pool should be frozen before final selection.

The final case should be selected mechanically where practical.

Cases should not be chosen because they already contain explicit language similar to IDOS concepts.

## Sampling Objective

V002 tests whether IDOS begins to become more useful as AI moves from:

\[
Tool
\]

toward:

\[
Infrastructure
\]

The key question is:

\[
Does\ incremental\ visibility\ emerge
\ when\ AI\ becomes\ structurally\ embedded?
\]

---

# 23A.3 Case V003 — Transition Sampling

## Regime Purpose

V003 represents a system undergoing active structural transition.

The defining feature is not simply high AI capability.

Rather, the case should contain movement in one or more of the following:

- decision authority;
- organizational role allocation;
- Human–AI responsibility boundaries;
- escalation structures;
- measurement systems;
- accountability structures;
- Updating Unit;
- operational boundaries.

Conceptually:

\[
B_t \neq B_{t+1}
\]

and potentially:

\[
U_t \neq U_{t+1}
\]

where \(B\) represents the relevant boundary and \(U\) the Updating Unit.

## Inclusion Criteria

A candidate case should show observable evidence that roles or system structure changed over time.

Possible patterns include:

- humans moving from decision-makers to supervisors;
- AI moving from recommender to executor;
- organizations reorganizing work around AI systems;
- responsibility migrating across organizational boundaries;
- machine outputs becoming the dominant basis for action;
- previously external AI systems becoming internal operational dependencies.

The case should contain enough temporal evidence to reconstruct the transition.

## Sampling Rule

The candidate pool should include multiple cases of documented structural transition.

Cases should be selected based on pre-defined transition criteria rather than on whether the transition appears to validate IDOS.

The final case should be selected after the candidate pool is frozen.

## Sampling Objective

V003 directly tests the concepts of:

- Dynamic Boundary;
- Updating Unit;
- Trajectory;
- Future Updateability.

The key question is:

\[
Does\ IDOS\ reveal\ something
\ specifically\ because\ the\ system\ itself
\ is\ changing\ what\ counts\ as\ the\ system?
\]

---

# 23A.4 Case V004 — Agentic / Multi-Agent Sampling

## Regime Purpose

V004 represents systems in which multiple autonomous or semi-autonomous agents interact.

The agents may include:

- AI agents;
- humans;
- organizations;
- automated services;
- algorithmic markets;
- machine-mediated institutions.

The defining characteristic is distributed interaction rather than a simple Human–AI pair.

Expected structural characteristics include:

- chained delegation;
- machine-to-machine interaction;
- distributed execution;
- indirect human supervision;
- fragmented provenance;
- propagation of outputs across agents;
- possible mismatch in update speed;
- difficulty locating effective control.

Conceptually:

\[
Agent_i
\rightarrow
Agent_j
\rightarrow
Agent_k
\rightarrow
Action
\]

with no single actor necessarily observing the entire chain.

## Inclusion Criteria

A candidate case should contain:

1. multiple interacting decision or execution agents;
2. meaningful autonomy or semi-autonomy;
3. propagation of outputs between agents;
4. limited direct human visibility over the full interaction chain;
5. reconstructable evidence of system behavior.

The case may be contemporary, experimental, or advanced deployment, but should remain empirically grounded.

## Sampling Rule

A candidate pool should include multiple eligible multi-agent or agentic systems.

The candidate pool must be frozen before selection.

The final case should not be selected merely because it demonstrates provenance failure, verification failure, or update blockage.

Those outcomes must remain empirical questions.

## Sampling Objective

V004 particularly tests:

- CFV;
- MU;
- Provenance;
- Temporal Compatibility;
- update propagation;
- blockage of update across agents;
- distributed responsibility.

The key question is:

\[
Can\ conventional\ analysis
\ adequately\ describe
\ who\ can\ verify,\ influence,\ and\ update\ whom?
\]

and:

\[
Does\ IDOS\ add\ structure
\ once\ interaction\ becomes\ distributed?
\]

---

# 23A.5 Case V005 — Future Regime Proxy Sampling

## Regime Purpose

V005 represents the nearest empirically defensible proxy for a future society in which AI, humans, organizations, and institutions become deeply interdependent and dynamically co-updating.

This is not a speculative science-fiction case.

V005 must remain grounded in observable or reproducible present-day evidence.

However, it should contain multiple structural properties expected to become more important under advanced AI conditions.

These may include:

- autonomous agent interaction;
- dynamic delegation;
- rapidly changing operational boundaries;
- machine-generated measurement systems;
- high-speed AI decision cycles;
- reduced direct human observability;
- recursive workflow adaptation;
- AI-mediated organizational restructuring;
- provenance fragmentation;
- distributed governance;
- human oversight lag;
- machine-to-machine coordination;
- unstable Updating Units.

Conceptually:

\[
Present\ Evidence
\rightarrow
Future\ Structural\ Proxy
\]

not:

\[
Speculation
\rightarrow
Future\ Claim

## Sampling Rule

A candidate pool should be constructed from multiple systems that satisfy the pre-defined future-regime markers.

The pool must be frozen before final selection.

If no single present-day case satisfies the required structural complexity, a composite proxy may be constructed only under explicit rules.

1. separate observed facts from extrapolated structure;
2. identify the empirical source of each component;
3. avoid assuming ASI capabilities not currently evidenced;
4. preserve traceability from present evidence to future-regime property;
5. state clearly which aspects are observed, simulated, or inferred.

The final V005 case must not be chosen because it maximizes apparent IDOS relevance.

# 23A.6 Cross-Regime Sampling Constraint

The five cases should not be interpreted as five independent examples only.

Together they form a structured regime gradient:

\[
V001
\rightarrow
V002
\rightarrow
V003
\rightarrow
V004
\rightarrow
V005
\]

The cross-case analysis should therefore examine whether incremental visibility changes as structural complexity increases.

However, the protocol must not assume monotonic improvement.

The following are all valid possible outcomes:

\[
Y_1 \approx Y_2 \approx Y_3 \approx Y_4 \approx Y_5
\]

\[
Y_1 < Y_2 < Y_3 < Y_4 < Y_5
\]

\[
Y_1 \approx 0,\quad Y_3>0,\quad Y_5>0
\]

or any other observed pattern.

The regime gradient is therefore a test structure, not a predicted result.

# 23A.7 Candidate Pool Freeze Rule

Before analyzing a selected case with IDOS, the following information should be preserved:

- regime definition;
- inclusion criteria;
- candidate pool;
- exclusion reasons where applicable;
- selection method;
- selected case;
- date of freeze.

Once the final case is selected, it should normally not be replaced because:

- the evidence is inconvenient;
- IDOS performs poorly;
- conventional analysis performs too well;
- the case does not reveal the expected structure.

Replacement is allowed only for procedural reasons, such as:

- insufficient evidence;
- inaccessible source material;
- mistaken regime classification;
- duplicate case structure;
- material factual error discovered before substantive analysis.

Any replacement should be documented.

# 23A.8 Sampling Interpretation

This five-case pilot is not designed to estimate population frequencies or statistical effect sizes.

The intended inference is therefore:

\ does\ IDOS\ add\ visibility?
\]

rather than:

\[
How\ common\ is\ IDOS\ value
\ across\ all\ systems?

The sampling design should be understood accordingly.
