## Three-Level Validation Protocol for IDOS Architecture-Level Added Value

**Protocol Version:** v0.1  
**Status:** FREEZE CANDIDATE  
**Date:** 2026-10-02  
**Architecture Baseline:** MASTER_MAP_v1.0 — FROZEN  
**Related Protocols:** FUTURE_REGIME_VALIDATION_PROTOCOL_v0.1 / Present-Day Case Program

**Retrospective Rule:** CASE-F001 is not re-scored as a confirmatory case under this protocol.

# 0. Purpose

This protocol extends the IDOS validation program from construct-level testing to explicit architecture-level testing.

The existing case program can determine whether individual IDOS constructs are:

- necessary;
- distinguishable;
- observable;
- measurable;
- contradicted;
- replaceable by simpler or established concepts.

However, the validity or usefulness of individual constructs does not by itself establish the value of the architecture as a whole.

The central problem is:

\[
\boxed{
\text{Value of Parts}
\neq
\text{Value of Architecture}
}
\]

Likewise:

\[
\boxed{
\sum_i \text{Construct Support}_i
\not\Rightarrow
\text{Architecture Added Value}
}
\]

The purpose of this protocol is therefore to test whether the **organization, connection, and integration of IDOS constructs** provides explanatory, diagnostic, measurement, governance, or compression value beyond what can be achieved by the best available combination of rival frameworks.

The central question is:

\[
\boxed{
\text{Does the organization of the parts matter?}
}
\]

More operationally:

\[
\boxed{
\text{Does IDOS as an architecture add value beyond its individual constructs and beyond a strong rival-framework combination?}
}
\]

---

# 1. Why Architecture-Level Validation Is Necessary

An architecture can fail even if many of its components are individually reasonable.

For example:

- Measurement may be useful.
- Power Asymmetry may be useful.
- Relational Update may be useful.
- Re-measurability may be useful.
- Mutual Updateability may be useful.

Yet the architecture connecting these ideas may still be:

- redundant;
- unnecessarily complex;
- poorly ordered;
- weakly integrated;
- explanatorily neutral;
- inferior to a simpler combination of established frameworks.

Conversely, individual concepts may be non-novel while their organization creates useful higher-order structure.

Therefore:

\[
\boxed{
\text{Construct Novelty}
\neq
\text{Architectural Value}
}
\]

and:

\[
\boxed{
\text{Non-Novel Parts}
\not\Rightarrow
\text{Non-Valuable Architecture}
}
\]

This protocol tests that second question directly.

# 3. Three-Level Validation Structure

Every applicable case is evaluated at three distinct levels.

\[
\boxed{
\text{Level 1}
\rightarrow
\text{Level 2}
\rightarrow
\text{Level 3}
}
\]

where:

\[
\boxed{
\text{Level 1 = Construct Validation}
}
\]

\[
\boxed{
\text{Level 2 = Relational / Integrative Validation}
}
\]

\[
\boxed{
\text{Level 3 = Architecture-Level Validation}
}
\]

These levels must remain analytically distinct.

---

# 4. Level 1 — Construct Validation

Level 1 retains the existing case-level construct test.

For each relevant IDOS construct ask:

1. Is it necessary?
2. Is it distinguishable from adjacent concepts?
3. Is it observable, inferred, or unobservable?
4. Can it be operationalized?
5. Can a simpler or established concept replace it?
6. Does its explanatory or operational value exceed its complexity cost?

The default case-level judgment remains:

\[
A = \text{Strongly required}
\]

\[
B = \text{Plausible / useful}
\]

\[
C = \text{Unnecessary / unsupported}
\]

\[
X = \text{Contradicted}
\]

Level 1 evaluates **parts**.

It does not establish architecture-level value.

---

# 5. Level 2 — Relational / Integrative Validation

Level 2 tests whether the **connections among constructs** add information that is lost when the constructs are evaluated independently.

For each important chain or dependency ask:

> If the constructs remain but their proposed relation is removed, does explanatory, diagnostic, measurement, or intervention value decline?

For candidate constructs \(K_i\) and \(K_j\):

\[
\boxed{
K_i
\rightarrow
K_j
}
\]

must be evaluated separately from:

\[
\boxed{
K_i,\ K_j
}
\]

A successful Level 2 result requires more than co-occurrence.

It requires evidence that the relation itself matters.

---

# 6. Relation Necessity Test

For every proposed relation ask:

### R1 — Dependency

Does change in \(K_i\) alter the interpretation, measurability, or consequence of \(K_j\)?

### R2 — Ordering

Would reversing or removing the proposed ordering alter the analysis?

### R3 — Mediation

Does \(K_j\) explain how or why \(K_i\) propagates to a later condition?

### R4 — Cross-Level Link

Does the relation connect levels that rival analyses usually leave separate?

Examples:

- Unit → Relation
- Relation → System
- Measurement → Governance
- Verification → Updateability
- Local performance → Future Updateability

### R5 — Failure Propagation

Does the relation reveal how a local failure propagates through the larger system?

---

# 7. Level 2 Judgment

Use:

\[
A_R = \text{Relation strongly required}
\]

\[
B_R = \text{Relation useful but replaceable}
\]

\[
C_R = \text{Relation adds little beyond juxtaposition}
\]

\[
X_R = \text{Proposed relation is contradicted or misleading}
\]

Do not infer \(A_R\) merely because both endpoint constructs received Level 1 = A.

Formally:

\[
\boxed{
A(K_i) + A(K_j)
\not\Rightarrow
A_R(K_i\rightarrow K_j)
}
\]

---

# 8. Level 3 — Architecture-Level Validation

Level 3 evaluates IDOS as an organized architecture.

The central comparison is not:

\[
\text{IDOS}
\quad vs. \quad
\text{one rival theory}
\]

but:

\[
\boxed{
\text{IDOS}
\quad vs. \quad
\text{Best Rival Combination}
}
\]

The rival baseline should be allowed to combine multiple established frameworks where appropriate.

Examples may include:

- control theory;
- cybernetics;
- complex adaptive systems;
- multi-agent systems;
- distributed systems;
- game theory;
- active inference;
- network science;
- institutional analysis;
- safety engineering;
- measurement theory;
- governance frameworks;
- domain-specific models.

The burden remains on IDOS.

---

# 9. Best Rival Combination Rule

The analyst must construct the strongest reasonable non-IDOS account of the case.

The rival combination must not be intentionally weakened.

It should include every established framework that a competent analyst would reasonably use.

The test is:

\[
\boxed{
\text{IDOS}
\stackrel{?}{>}
\text{Best Rival Combination}
}
\]

where \(>\) does not mean superior in every respect.

It means that IDOS adds at least one meaningful capability that is not obtained as clearly, compactly, coherently, or operationally from the rival combination.

---

# 10. Counterfactual Without IDOS

Every case must include a section titled:

## Counterfactual Without IDOS

It must answer:

> If IDOS did not exist, and the case were analyzed using the strongest reasonable combination of existing frameworks, what would be lost?

Possible answers include:

- nothing material;
- only terminology;
- cross-level integration;
- a causal or structural dependency;
- a failure mode;
- an intervention point;
- traceability across scales;
- measurement continuity;
- future updateability;
- architectural compression.

If almost nothing is lost:

\[
\boxed{
Architecture\ Added\ Value \approx 0
}
\]

This is an acceptable result.

---

# 11. Architecture-Level Evaluation Dimensions

At minimum evaluate the following five dimensions.

---

## 11.1 Diagnostic Gain

Does IDOS identify a problem, distinction, dependency, or failure that the Best Rival Combination does not identify as clearly?

\[
DG
\]

Questions:

- Was a hidden failure mode exposed?
- Was a local success / system failure distinction revealed?
- Was an unrecognized measurement or governance dependency identified?

---

## 11.2 Relational / Cross-Scale Gain

Does IDOS connect phenomena across:

- Human;
- AI;
- Organization;
- Institution;
- Relation;
- Ecosystem;
- Measurement;
- Governance;

more coherently than the rival combination?

\[
RG
\]

This dimension is especially relevant to the Master Map hierarchy:

\[
\text{Individual Update}
\rightarrow
\text{Relational Update}
\rightarrow
\text{System Update}
\]

---

## 11.3 Failure Detection Gain

Does IDOS detect a failure mode that remains hidden or fragmented under rival approaches?

\[
FG
\]

Examples:

- performance improvement with declining updateability;
- verification without influence;
- local improvement with system degradation;
- measurement change destroying comparability;
- coordination without mutual update.

---

## 11.4 Intervention Gain

Does IDOS identify a different or additional intervention point?

\[
IG
\]

Examples:

- not only changing behavior but changing measurement;
- not only increasing observability but restoring influence;
- not only correcting a Unit but modifying relations;
- not only improving current performance but preserving future updateability.

A different label for the same intervention does not count as gain.

---

## 11.5 Compression Gain

Does IDOS represent the relevant structure more compactly or coherently than the Best Rival Combination?

\[
CG
\]

Compression does not mean fewer words.

It means:

> fewer independent explanatory structures are required to preserve the distinctions relevant to the case.

A provisional conceptual expression is:

\[
\boxed{
CG
=
\frac{
\text{Relevant Structure Preserved}
}{
\text{Independent Explanatory Machinery Required}
}
}
\]

This is not yet a canonical quantitative metric.

It is an evaluation principle.

---

# 12. Optional Sixth Dimension — Transfer Gain

Where appropriate, evaluate:

\[
TG
\]

for cross-domain transfer.

Question:

> Can the same IDOS architecture be applied across materially different domains without redefining its core relations ad hoc?

For example:

\[
Human
\leftrightarrow
AI
\]

\[
Organization
\leftrightarrow
AI
\]

\[
Institution
\leftrightarrow
Multiple\ AI\ Systems
\]

If the architecture works only after domain-specific reinterpretation so extensive that the common structure disappears, Transfer Gain is weak.

---

# 13. Architecture Added Value Judgment

After evaluating the dimensions, assign one overall architecture-level judgment.

\[
A_A
=
\text{Clear architecture-level added value}
\]

\[
B_A
=
\text{Some integrative added value}
\]

\[
C_A
=
\text{Mostly re-description / little added value}
\]

\[
X_A
=
\text{Architecture obscures, misclassifies, or degrades analysis}
\]

The subscript \(A\) denotes **Architecture**, not the Level 1 construct judgment.

---

# 14. No Mechanical Averaging Rule

The overall architecture judgment must not be produced by a simple average of Level 1 construct scores.

Forbidden logic:

\[
\boxed{
\text{Many A constructs}
\Rightarrow
A_A
}
\]

Similarly, do not mechanically average \(DG, RG, FG, IG, CG\).

A case may have:

- weak novelty;
- strong compression;
- no new intervention;
- strong cross-scale integration.

The overall judgment must explain the pattern.

---

# 15. Architecture as Compression Hypothesis

A central hypothesis to test is:

\[
\boxed{
\text{Architecture as Compression}
}
\]

The hypothesis is not that IDOS replaces domain theories.

It is:

> IDOS may provide a common higher-order organization through which multiple domain-specific theories can be related without being unified into one internal representation.

The architecture is valuable if:

\[
\boxed{
\text{IDOS}
+
\text{Domain-Specific Models}
}
\]

requires less disconnected explanatory machinery than:

\[
\boxed{
Framework_1
+
Framework_2
+
\cdots
+
Framework_n
}
\]

while preserving relevant distinctions.

This hypothesis must be tested, not assumed.

---

# 16. Architecture as Compression — Failure Condition

Compression fails if IDOS:

- adds terminology without reducing fragmentation;
- hides domain-specific distinctions;
- forces heterogeneous mechanisms into false equivalence;
- requires extensive reinterpretation in every case;
- produces no additional diagnosis or intervention;
- cannot outperform a concise rival synthesis.

In such cases:

\[
\boxed{
CG \leq 0
}
\]

conceptually, and architecture-level weakening pressure should be recorded.

---

# 17. Integration Versus Aggregation Test

A major distinction is:

\[
\boxed{
Integration
\neq
Aggregation
}
\]

Aggregation means:

> multiple useful concepts are listed together.

Integration means:

> explicit dependencies among the concepts generate additional explanatory or operational value.

For each case ask:

> If the arrows are removed and only the boxes remain, what is lost?

If the answer is:

> almost nothing,

then the case provides weak support for IDOS as an architecture.

---

# 18. Arrow Deletion Test

For every architecture-level chain identified in a case:

\[
K_1
\rightarrow
K_2
\rightarrow
K_3
\]

perform a conceptual ablation:

\[
K_1
\quad
K_2
\quad
K_3
\]

without the relations.

Ask whether the analysis loses:

- causal organization;
- temporal organization;
- propagation structure;
- intervention logic;
- measurement logic;
- governance logic.

This is the **Arrow Deletion Test**.

---

# 19. Node Deletion Versus Arrow Deletion

Construct validation and architecture validation therefore differ:

### Node Deletion

\[
\boxed{
\text{Remove }K_i
}
\]

Question:

> Is the construct necessary?

### Arrow Deletion

\[
\boxed{
\text{Remove }K_i\rightarrow K_j
}
\]

Question:

> Is the architecture necessary?

This distinction must be preserved in all prospective cases.

---

# 20. Architecture Ablation Test

Where feasible, compare:

### Model A — Full IDOS

Relevant nodes + relevant relations.

### Model B — IDOS Nodes Only

Same concepts without the proposed architecture.

### Model C — Best Rival Combination

Strongest reasonable non-IDOS analysis.

The strongest architecture-level evidence occurs when:

\[
\boxed{
Model\ A
>
Model\ B
}
\]

and:

\[
\boxed{
Model\ A
>
Model\ C
}
\]

on at least one meaningful dimension.

If:

\[
Model\ A
\approx
Model\ B
\]

then the architecture adds little beyond its parts.

If:

\[
Model\ A
\approx
Model\ C
\]

then any value may be primarily compression or common-language value.

If:

\[
Model\ A
<
Model\ C
\]

then the case generates architecture-level weakening pressure.

---

# 21. Architecture Failure Criteria

A case generates strong architecture-level weakening or contradiction pressure if one or more of the following occurs:

1. IDOS adds no meaningful result beyond the Best Rival Combination.
2. The architecture requires relations not supported by the case.
3. Proposed arrows create false causal or temporal implications.
4. Cross-scale integration erases important domain differences.
5. Full IDOS performs worse than an IDOS-nodes-only analysis.
6. Architecture terminology makes intervention points less clear.
7. The same phenomenon requires materially different interpretations of the same IDOS relation across cases.
8. Compression is negative: IDOS adds machinery without reducing fragmentation.
9. The architecture systematically over-detects relational or system-level phenomena.
10. The architecture prevents a simpler explanation from being recognized.

A contradiction-level result may be recorded as:

\[
\boxed{
Architecture\ Contradiction = YES
}
\]

where the failure cannot be repaired locally without altering the frozen architecture.

---

# 22. Architecture Non-Failure Conditions

The following do not by themselves constitute architecture failure:

- one construct receives C;
- one relation receives C_R;
- one architecture dimension shows no gain;
- IDOS concepts are non-novel individually;
- a rival framework explains part of the case better;
- 12PDM is unnecessary;
- a case is adequately described without some provisional construct.

IDOS need not dominate every analytical dimension.

---

# 23. Rival Superiority Is an Acceptable Result

The protocol must permit:

\[
\boxed{
\text{Best Rival Combination}
>
\text{IDOS}
}
\]

This is not a protocol failure.

It is evidence.

Likewise:

\[
\boxed{
\text{IDOS Added Value} = 0
}
\]

is an acceptable case result.

If such results cannot occur, the protocol is not falsification-sensitive.

\[

\]

\[

\]

must remain separate.

Therefore:

\[
\boxed{
Empirical\ Architecture\ Evidence
\neq

}
\]

A strong F-case architecture result does not empirically validate IDOS.

A weak P-case result does not establish failure under future complexity.

---

# 25. Cross-Case Architecture Pressure

Across cases, record at least:

\[
A_A,\ B_A,\ C_A,\ X_A
\]

separately for Track P and Track F.

Do not canonicalize architecture-level claims from a single case.

Possible patterns include:

### Pattern 1 — Cross-Regime Architecture Support

Repeated \(A_A/B_A\) in both P and F.

### Pattern 2 — Present Weak / Future Strong

Mostly \(C_A\) in P, stronger \(A_A/B_A\) in F.

Interpretation:

> architecture may become useful primarily under high complexity.

### Pattern 3 — Present Strong / Future Weak

Architecture useful today but unstable under future complexity.

### Pattern 4 — Cross-Regime Weakening

Repeated \(C_A/X_A\) in both tracks.

This creates strong pressure to simplify or replace the architecture.

# 29. Interpretation Discipline

Architecture-level value must not be inferred from elegance.

Do not treat the following as evidence by themselves:

- the case maps cleanly;
- many nodes can be identified;
- a diagram looks coherent;
- the architecture is broad;
- multiple disciplines appear inside the map;
- IDOS terminology can redescribe the case.

The burden is:

\[
\boxed{
Added\ Value
>
Added\ Complexity
}
\]

at the architecture level.

---

# 30. Novelty Discipline

This protocol does not test historical originality by itself.

Architecture Added Value and novelty are separate questions.

\[
\boxed{
Architecture\ Added\ Value
\neq
Historical\ Novelty
}
\]

A result may show:

- useful integration;
- useful compression;
- useful intervention logic;

without establishing that no prior architecture has done something equivalent.

Novelty requires a separate literature and equivalence analysis.

---

# 31. Measurement Discipline

Architecture-level judgments should be treated as qualitative until the gain dimensions are operationalized.

Do not convert:

- Strong;
- Moderate;
- Weak;
- None;
- Negative;

into arbitrary numerical totals merely to create an apparent quantitative score.

Quantification may be introduced only after:

- coding rules;
- inter-rater procedure;
- examples;
- disagreement handling;
- calibration;
- reliability checks;

are defined prospectively.

---

# 33. Protocol Success Criteria

This protocol is useful if it can distinguish at least some cases where:

1. individual IDOS constructs are useful but the architecture adds no value;
2. architecture adds value despite low construct novelty;
3. rival-framework combinations outperform IDOS;
4. IDOS adds cross-scale structure not recovered by nodes alone;
5. compression gain appears without diagnostic novelty;
6. intervention gain appears even when explanatory gain is small;
7. future-regime architecture value differs from present-day architecture value;
8. architecture-level weakening accumulates across cases.

---

# 34. Protocol Failure Criteria

Revise this protocol if:

- almost every case receives \(A_A\) or \(B_A\);
- the Best Rival Combination is routinely under-specified;
- Counterfactual Without IDOS becomes rhetorical rather than analytical;
- Arrow Deletion does not produce discriminating results;
- Full IDOS and Nodes-Only cannot be meaningfully distinguished;
- Compression Gain cannot be defined consistently;
- evaluator discretion dominates results;
- architecture judgments simply mirror Level 1 construct judgments.
